01

What Git actually is

Git takes snapshots of your project over time. Each snapshot is a commit — a save point you can always come back to. GitHub is just a website that hosts a copy of your Git project so others (and you, from another machine) can reach it.

Working directory→ git add →Staging area→ git commit →Local repo (.git)→ git push →GitHub

Install it

Check whether you already have it:

git --version

If that errors, grab it for your OS:

OSCommand / link
Windowsgit-scm.com/download/win (installer)
macOSbrew install git
Linux (Debian/Ubuntu)sudo apt install git

Introduce yourself to Git

Git stamps every commit with a name and email — set these once, globally:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
Check it worked Run git config --list to see everything Git has stored for you.
02

Your first repository

A "repo" is just a folder Git is watching. Turn any folder into one:

mkdir my-project
cd my-project
git init

That creates a hidden .git folder — that's the entire database of your project's history. Delete it and the folder goes back to being a plain, untracked directory.

Add a file

echo "# My Project" > README.md
git status

git status is the command you'll run constantly — it tells you exactly what Git sees: what's changed, what's staged, what's untracked. Right now it'll call README.md untracked, meaning Git knows it exists but isn't watching it yet.

03

Staging and committing

Git splits "save" into two steps on purpose: stage what you want in the next snapshot, then commit it. This lets you commit only part of what you changed.

git add README.md        # stage one file
git add .                 # stage everything changed
git commit -m "Add README"

Write commit messages in the imperative, like an instruction: "Fix login bug", not "fixed a bug". Keep the first line under ~50 characters.

Tagging a release

Once a commit represents something meaningful — a version — mark it:

git tag v1.0.0
git push origin v1.0.0   # tags don't push automatically

Stashing work-in-progress

Need to switch tasks without committing half-finished work?

git stash              # shelve your changes
git stash list
git stash pop           # bring them back
04

Reading and rewriting history

Look at what happened

git log                   # full history
git log --oneline --graph # compact, visual

Undoing things

Pick the right tool based on where the mistake lives:

SituationCommand
Undo an already-pushed commit safelygit revert <commit>
Throw away local commits, keep the codegit reset --soft HEAD~1
Throw away local commits and the codegit reset --hard HEAD~1
Fix the message/contents of the last commitgit commit --amend
"I deleted a branch/commit, help"git reflog
Careful git reset --hard deletes uncommitted work permanently. git revert is the safe one for anything already shared with others — it adds a new commit that undoes the old one instead of erasing history.
05

Branching & merging

A branch is a separate line of work. You almost always want to build a feature on its own branch, not directly on main.

git branch                    # list branches
git branch feature-login      # create one
git checkout feature-login    # switch to it
git checkout -b feature-login # create + switch in one step

Do your work, commit as usual, then bring it back into main:

git checkout main
git merge feature-login
Merge conflicts If both branches edited the same lines, Git stops and marks the conflict directly in the file with <<<<<<< / ======= / >>>>>>> markers. Edit the file to keep what you want, delete the markers, then git add the file and git commit to finish the merge.

A typical workflow

Most teams follow some version of "GitHub Flow": main is always deployable, every change happens on a short-lived branch, and you open a pull request to bring it back in.

06

Connecting to GitHub

GitHub just hosts a copy of your repo, called origin by convention. Two ways to authenticate: HTTPS (username/token) or SSH (a keypair, no password each time).

Option A — HTTPS (simplest to start)

  1. Create an empty repo on github.com/new — don't add a README if you already have one locally.
  2. Link your local repo to it: 
    git remote add origin https://github.com/USERNAME/REPO.git
  3. Push your history up: 
    git branch -M main
git push -u origin main
    The -u remembers this pairing, so afterward a plain git push is enough.

Option B — SSH (no password prompts)

ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub   # copy this into GitHub → Settings → SSH keys

Then use the SSH remote URL instead: git remote set-url origin git@github.com:USERNAME/REPO.git

Everyday sync

git pull                  # bring down others' changes
git push                  # send your commits up
git push origin feature-login   # push a specific branch
07

Working with other people's repos

Cloning

Download a full copy of any repo, history included:

git clone https://github.com/USERNAME/REPO.git

Contributing to someone else's project

  1. Fork it on GitHub — this makes your own copy under your account.
  2. Clone your fork, make a branch, commit your change.
  3. Push the branch to your fork: 
    git push origin my-fix-branch
  4. On GitHub, click Compare & pull request to send it back to the original project for review.
08

Habits worth building early

.gitignore

Tell Git what to never track — dependencies, build output, secrets:

node_modules/
.env
*.log

Commit often, in small pieces

One logical change per commit. It makes git log, git revert, and reviewing diffs dramatically easier later.

A minimal daily loop

git pull                          # start with the latest
git checkout -b my-change         # branch for the task
# ... edit files ...
git add .
git commit -m "Do the thing"
git push -u origin my-change      # then open a pull request
If you're stuck git status first, always. It tells you exactly what state you're in and often suggests the next command directly in its output.
